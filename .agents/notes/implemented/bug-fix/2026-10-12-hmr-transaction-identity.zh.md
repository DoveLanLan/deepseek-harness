# Agent Note: HMR 事务按身份而非继承标记判定嵌套

Status: implemented

[English](2026-10-12-hmr-transaction-identity.md) | 中文

## Problem

Web GUI 的设置写入在一个 `dsh web` 进程的整个生命周期内都返回 `HMR transactions cannot be nested`，而 profile 重载本身始终正常。`Hmr.runExclusive()` 的守卫把调用方的异步上下文读作「有事务正在运行」，但这种读法只对当前持有队列的那个事务成立：`AsyncLocalStorage` 同样会把事务的存储交给事务期间创建的每个资源——定时器、监听器、HTTP 服务——并且在该资源余下的生命周期内一直保留。Web 监听器就是生产环境中的实例：profile 重新组合会在事务内销毁并重建插件条目，而 Node 会把此后每个请求的异步上下文接到接受该请求的监听器的 accept 上下文上。于是每个请求都继承了一个事务已经结束的标记，浏览器里的每次写入都被判为嵌套事务。相同组合的全新进程可以接受同一写入，这正是它与 profile 配置错误的分界。

## Decision

HMR 的异步上下文携带每个事务一个的 token，而不是布尔值。`Hmr.runExclusive()` 只在继承到的 token 就是当前持有队列的事务身份时才拒绝；持有已结束事务 token 的调用者与其他调用者一样排在队尾。标记的另外两处读取同样按身份比较：HMR 销毁器只在运行中的事务内部才跳过等待待处理操作，精确配置监听也只在运行中的事务内部才跳过排空自己的刷新。

队列无法推进的场合仍然拒绝，因为运行中的事务就是队尾：该事务等待的调用者会在等它自己。已结束的事务不等待任何东西，队列正是继承其上下文的调用者所需要的串行化。

## Alternatives considered

**保留布尔标记并拒绝所有继承的上下文。** 这就是缺陷本身：重载期间创建的每个资源会一直带着标记，此后经由该资源提交的工作都无法落地。

**在事务结束时清除标记。** `AsyncLocalStorage.run()` 无法从事务内部已创建的资源上收回存储；只有此后创建的资源才会看到变化。

**在创建长生命周期资源处逃逸环境上下文**，例如在 Web 监听器处。所属包无法触达另一个服务的 `AsyncLocalStorage` 实例，而且每个在重载期间创建监听器、定时器或监听器的子系统都有同样的隐患，守卫是唯一能看到全部场合的位置。

**直接拒绝并要求重启。** 重启会清除标记，但会丢弃每个正在运行的会话进程，而且同样的重载会再次产生同样的标记。

## Consequences

继承自已结束事务的工作现在排在队列之后执行，而不是直接失败，因此在重载期间启动的监听器或定时器之后仍可提交配置写入；Web GUI 的预设默认项写入能在监听器于事务内重启过的进程中落地。有针对性的重入保护不变：在运行中的事务内部发起的调用仍被拒绝，这由现有的协调用例固定。代价是：依赖该拒绝来检测自身重入的子系统，其工作会改为延后执行；当前没有消费者出于该目的读取标记，因为标记是本服务私有的。

## Testing

`packages/boot/hmr/tests/coordination.spec.ts` 保留在运行中的事务内部拒绝调用的现有用例，并新增两个：从事务内部创建的定时器上排入的工作会兑现；在事务内启动的真实 `node:http` 监听器会服务一个其处理器调用 `runExclusive()` 的请求。监听器用例在本变更前以 `HMR transactions cannot be nested` 失败。
